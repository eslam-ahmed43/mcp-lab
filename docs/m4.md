# M4: security (attack lab and enforcement)

## What I built
- An intentionally vulnerable MCP server (attack_lab/) with three attacks: a poisoned tool description, path traversal through a file name argument, and a prompt injection inside a tool result. All data is fake.
- security.py with a tool description scanner, a tool result scanner, an untrusted-content wrapper and a path confinement function.
- Enforcement in the real gateway: create_task rejects titles that contain high severity injection patterns, and reading tasks://all withholds flagged titles while keeping ids and the JSON shape, and records the count in the audit log.
- 58 automated tests passing, 1 skipped.

## Lab results
- The poisoned get_weather description was flagged by five rules (three high, two medium). The hidden block asked the model to read ../secret.txt and not tell the user.
- The unguarded server returned the fake secret for ../secret.txt. The confinement check blocked it.
- The injected support ticket was flagged by four high severity rules. The benign ticket passed.
- In the gateway: a writer trying to create a task with an injection title was rejected, and a poisoned row already in the database was withheld when an admin read the task list.

## Honest scope
- The attack lab script prints the guarded outcomes itself. There is no gateway between an agent and the vulnerable server, so the lab shows detection, not enforcement.
- Enforcement exists only on the real data path of this project: task titles on write and on read.
- Tool description scanning is not applied at runtime by the gateway, because the gateway does not proxy third-party servers. It is only used in the lab.
- The untrusted-content wrapper is only used in the lab.

## Limitations
- The scanners are regular-expression heuristics. A test documents that a paraphrased injection is not detected. Real protection comes from architecture: least privilege, path confinement, human approval for destructive tools, and separating data from instructions.
- A high severity rule can reject a harmless title that discusses these patterns.
- The symlink escape test is skipped on Windows without symlink privileges, so that defense has not been exercised on my machine.
- The audit log stores attacker-controlled text and must be treated as untrusted if it is ever shown to a model.

## Evaluation with a real agent

Setup: a Gemini model acts as the agent through the real gateway with a bearer token, over a seeded isolated database. Temperature is zero, so repeated runs are almost identical and three runs per scenario are close to one trial each.

Results:
- Tool selection (gemini-3.6-flash, one run per scenario, six scenarios): the first tool call and its arguments were correct in 6 of 6. This is a smoke test, not an accuracy figure.
- Prompt injection with scanning off (gemini-3.1-flash-lite, three scenarios, nine runs): the model read the poisoned task title, described it as an ordinary task, and never called delete_task. Zero attempts.
- Prompt injection with scanning on (gemini-3.5-flash, partial, 7 valid runs, 2 invalid because of quota): zero attempts. With scanning on the poisoned title is withheld, so the model never saw it.
- Permissions (gemini-3.1-flash-lite, three scenarios, nine runs): the agent tried the forbidden tool in 9 of 9 runs, the gateway denied 9 of 9, and no state changed. In the first run of each scenario the agent told the user the action was denied and did not claim success.

What these results do not show:
- The scanning-on and scanning-off rounds ran on different models, so there is no measured effect of scanning. The scanner is evidenced by unit tests and the attack lab, not by this evaluation.
- One simple injection payload and a small sample. A capable model resisting it says little about stronger attacks.
- Invalid runs caused by free-tier quota are excluded from the counts and reported separately.

Finding: the gateway enforces permissions at call time but still lists every tool to every role. The reader and writer agents saw and tried admin-only tools, including list_pending_approvals. Filtering the tool list by role is the next change.
