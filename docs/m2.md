# M2: gateway, auth and approvals

## What I built
- SQLite storage for the tasks backend.
- A FastMCP gateway that authenticates a bearer token, maps it to a role, and applies a policy returning ALLOW, DENY or REQUIRE_APPROVAL before forwarding any call.
- A human approval flow for delete_task: the request is queued, a different admin must approve it, and the requester cannot approve their own request.
- An append-only JSONL audit log with user, tool, arguments, decision and outcome for every call, including blocked ones.
- 12 pytest tests covering authentication, policy decisions and approval rules.

## Security finding
While the backend listened on its own HTTP port, any client could call it directly and skip the gateway entirely (verified with a direct client call). Fix: the gateway now launches the backend as a stdio subprocess, so there is no network port to bypass. Trade-off: one process spawn per call.

## Failure found in testing
An approval was granted for a task that had already been deleted. Execution failed, the approval stayed marked approved, and it could not be retried. Root causes: no existence check at request time, no execution status on the approval, and a non-idempotent delete. To be fixed in M3.

## Known limitations
- Tokens are hardcoded in auth.py. Production would use a secrets store and short-lived tokens.
- Approvals are in memory and lost on gateway restart.
- Audit log is a local file without tamper protection.
