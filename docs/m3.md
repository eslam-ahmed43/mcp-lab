# M3: reliability

## What I built
- Error classification with seven categories: VALIDATION, NOT_FOUND, PERMISSION, RATE_LIMIT, TIMEOUT, UNAVAILABLE, UNKNOWN. Backend errors carry a code prefix, so classification does not depend on message wording.
- Retry with exponential backoff and jitter, only for transient categories (RATE_LIMIT, TIMEOUT, UNAVAILABLE), at most four attempts. Every failed attempt is written to the audit log.
- Idempotent delete and complete. Deleting a missing task succeeds with an already_absent flag, and delete checks that the task exists at request time.
- Approval lifecycle with an execution status (not_run, executed, failed) and the failure reason. A retry_approval tool re-runs a failed approved execution and refuses if it already ran.
- Idempotency keys on create_task, enforced by a unique index in SQLite, namespaced per user in the gateway. Reusing a key with different arguments is rejected.
- Fault injection through the MCP_FAULTS environment variable, including after_* faults that fire after the backend already succeeded.
- 41 automated tests.

## Failures found
1. Approval granted for a task that no longer existed: execution failed, the approval stayed approved with no record of the failure, and it could not be retried. Fixed with request-time existence check, idempotent delete, execution status and retry_approval.
2. Lost response after a successful create without a key: the client saw TIMEOUT but the task existed (an orphan). With a key, the retry returned the same task. Reproduced live and in tests: three tasks without a key, one task with a key.

## Measurements
- Backoff gaps between the four attempts of a failing delete grew roughly 0.2s, 0.4s, 0.7s.
- Spawning the backend per call costs about 4 to 5 seconds on my machine.

## Decisions and trade-offs
- create_task is retried only when an idempotency key is present. Without a key a retry could create a duplicate.
- Unknown errors are never retried, because repeating an operation of unknown cause may repeat a side effect.
- Any admin can retry a failed approved execution, including the requester, because the approval is still valid and delete is idempotent.
- Fault injection is configured only through the gateway process environment and is not exposed as a tool.

## Known limitations
- Idempotency keys never expire, so storage grows.
- A create_task call without a key can still leave an orphan when a response is lost. A production version should require the key.
- Approvals live in memory and are lost on restart.
- The backend is spawned for every call, which is slow. A persistent connection would fix it.
- No circuit breaker or rate limiting yet.
- Tokens are hardcoded.
