# M1: MCP fundamentals

## What I built
A FastMCP server (tasks-server) exposing two tools (create_task, complete_task), two resources (tasks://all and the template tasks://{task_id}) and one prompt (plan_my_day). It runs over stdio and over Streamable HTTP. A client discovers tools at runtime with list_tools and calls them.

## Tool vs resource vs prompt
- Tool: the model decides to call it and it performs an action.
- Resource: the application decides to load it as read-only context.
- Prompt: the user picks it, and it returns a ready-made message.

## What I observed
- Validation errors come back as a tool error inside the result, so the connection stays up and the model can see the message and retry.
- Over stdio every client starts a fresh server, so state resets. Over HTTP the server keeps state between requests and sessions.
- Every request over HTTP is a POST to the single /mcp endpoint.
- Tested with MCP Inspector and the JSON-RPC messages in its Protocol tab.

## What I would change
- Replace in-memory storage with SQLite.
- Add authentication and permissions (M2).
- Add tests for the tools and resources.
